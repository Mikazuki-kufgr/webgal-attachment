# WebGAL Live2D 动态附件：完整使用说明

本说明对应 `MYGO321-AUTO-FIGURE-SWITCH.7`；安装、制作与脚本按下述已验证路径操作。同版手部验收场景的独立网页、两状态存读档和 Terre 图形界面导出已有用户正常反馈；其他未验证能力见已知限制。

说明书修订：**2026-09-30 公测发布前核对**。本说明对应下方 `.7` 软件修订；此前公开的预告包保持原样。

适用版本：WebGAL Attachment **0.5.0-beta.1 / MYGO321-AUTO-FIGURE-SWITCH.7**，Windows x64、MyGO 3.2.1 / Terre 4.6.4 社区宿主的指定适配包。本说明随此安装包提供，**包含“另存为新附件”身份生成顺序及界面提示修复**。历史构建证据保留原修订名，现行操作以本说明及 FIRST_USE.md 为准；这份说明对应上述软件修订的操作。宿主身份和限制可另查同目录 `DISTRIBUTION.json`、`KNOWN_LIMITATIONS.md`。插件安装到已有 Terre；安装包不包含完整 Terre、人物模型或 Live2D SDK。安装完成并从已安装 Manager 验证通过后，可以删除下载 ZIP 和安装包解压目录；正常运行不依赖它们。保留实际宿主、Manager、Authoring 和游戏资料；需要的随包说明、演示素材先另存。原 ZIP 可选留作离线修复备份；删除后如需完整包修复，请重新下载对应版本。

这份说明按实际操作顺序编排。需要双击哪个文件、在哪个应用里操作、何时返回制作器或进入 Terre，都在对应步骤明确写出。剧情命令一节给出本插件命令的作用、参数、典型写法和易出错的交互；直接使用制作器与 Terre 的用户可先完成前半部分，再按需要查命令。

## 先看这张路线图

1. **安装插件**：解压安装包，完全关闭 Terre 和制作器，从**解压后的安装包根目录**双击 `01_安装或升级.cmd`，选择实际包含 WebGAL_Terre.exe 的宿主目录。安装完成后进入该宿主的 `release/WebGAL-Attachment-Manager/`，双击里面的 `03_验证安装.cmd`。
2. **制作附件**：在刚才的 **`release/WebGAL-Attachment-Manager/`** 双击 `02_打开附件制作器.cmd`，保持弹出的 CMD 日志窗口打开。选人物和具体服装/模型，载入立绘；选已有附件或透明 PNG；选跟随部位，调整图片；点击“保存附件”。这一步无需先建游戏。
3. **放进游戏**：在制作器第 5 步选择目标游戏，按提示确保人物模型已在该游戏，再点击“添加 / 更新到这个游戏”。然后打开所安装宿主的 `WebGAL_Terre.exe`，进入该游戏，在 Terre 的剧情列表搜索“附件测试”或附件名，并按制作器结果给出的 `game/scene/附件测试-…txt` 找到**独立验证剧情**检查效果。
4. **正式使用**：在 Terre 中编辑自己的剧情，调用同一人物、附件配置与锚点；先在普通播放中确认位置、动作跟随和遮挡，再从 Terre 导出游戏成品。附件的本地保存、附件文件夹导出、添加到游戏和游戏成品导出是四个不同动作。
5. **对照演示脚本**：安装包根目录另有不含人物模型的 `演示脚本与附件素材_林间草帽与赠花.zip`，解压后看 `game/scene/林间草帽与赠花.txt`；第 10 节按剧情顺序拆解草帽和花怎样在游戏里调用。这个资料包只供阅读和改编，**不是可直接启动的游戏**。

首次尝试建议使用测试游戏和一张简单的透明 PNG。不要直接拿唯一一份正式剧情或唯一一套手调附件做实验。

## 1. 安装与启动

1. 把整个 INSTALL 压缩包解压到一个普通本地文件夹，保留文件夹内的 `runtime`、`payload`、`resources`、`manifests` 等内容。不要只取出某个 `.cmd` 单独运行。
2. 关闭 WebGAL Terre、制作器页面及其 CMD、预览页面和相关启动器。双击 `01_安装或升级.cmd`，按窗口提示选择 **MyGO 3.2.1 / Terre 4.6.4 中实际包含 WebGAL_Terre.exe 的目录**，不是某个游戏的 `game` 文件夹。安装程序会先检查宿主与已有安装状态；报错时保留原文，不要通过删除安装记录或手动覆盖文件绕过。
3. 安装结束后，进入**所选宿主的** `release/WebGAL-Attachment-Manager/` 文件夹，双击里面的 `03_验证安装.cmd`。看到通过结果后，再双击这个 Manager 文件夹里的 `02_打开附件制作器.cmd`。它启动本机制作器服务并打开网页。制作器的 CMD 是实时日志窗口，使用期间保持打开；不要把关闭网页误认为已经停止服务。用完先关闭制作器网页，再运行同一 Manager 文件夹里的 `05_停止附件服务.cmd`。**不要从下载包的解压目录直接运行其中的 `02_打开附件制作器.cmd`**：下载包入口会明确说明正确启动位置，不读取旧安装请求自动跳转；安装成功提示会显示实际 Manager 入口的完整路径。
4. 从旧版升级时继续使用同一个宿主 `release`。制作资料与游戏资料应保留；若升级检查报告冲突，应先保存错误信息并停止，不要反复覆盖用户文件。Manager 文件夹里的 `04_修复安装.cmd` 用于安装记录允许的受管文件修复，不用于强制改写人物、附件或剧情。确需卸载时，在关闭相关程序后运行同文件夹的 `06_卸载插件.cmd`；卸载仍应保留用户资料。

安装不要求先创建游戏。插件也不会把所有现有游戏自动换成新引擎。启动宿主根目录的 `WebGAL_Terre.exe` 后，新建游戏时在“选择游戏引擎版本”核对 **MyGO 3.2.1 衍生引擎**，不要因为列表默认值或游戏名字就假定选对。已有游戏如果仍使用 WebGAL Standard/官方引擎，附件和 Live2D 可能无法运行；先核对该游戏实际引擎，再检查模型和资源。若新建游戏时 MyGO 选项为空，先看宿主 `release/必看.txt` 的引擎注册说明；该整合包提供的路径是 Terre 右上角“设置”→“4.6 用户数据迁移”→“开始迁移”。注册完成后再创建或核对测试游戏，不要把官方引擎黑屏当作 PNG 损坏。

## 2. 理解五个对象

| 看到的名称 | 它负责什么 | 常见误会 |
| --- | --- | --- |
| 人物与服装/立绘 | 指向这次实际显示的一套模型及其动作、贴图依赖 | 同一人物名下的不同外观不自动共用几何 |
| 锚点配置（Profile）与跟随部位 | 描述某套模型上可用的头、手、耳等跟随位置 | 同名部位不证明两个模型的网格相同 |
| 附件本体 | 保存一份或前后两层 PNG、显示名和稳定配置身份 | 改显示名不会自动建立新附件或改旧剧情引用 |
| 适配 | 同一附件在某个人物外观及锚点上的偏移、大小、角度等 | 新人物显示默认起点不等于已经校准 |
| 游戏中的实例 | 剧情播放时出现的一次附件 | 保存到制作器不等于已经添加到游戏 |

**保存附件**会更新当前附件；**另存为新附件**旨在生成另一套身份并保留原附件，本包已修复旧版因手改配置 ID 与保留适配冲突导致的另存失败；**添加 / 更新到这个游戏**会部署到所选游戏；**导出完整附件文件夹**用于备份或分享。这四个动作不要混用。显示名称可以是中文，普通用户不要手改配置 ID。

## 3. 第一次从 PNG 做附件

1. 在制作器第 1 步依次选“角色”和“服装 / 立绘”，点击“载入所选立绘”，等左侧画面出现**正确的具体外观**。若列表没有你的模型，先按下一节把已有立绘批量复制到制作区，或用页面按钮导入。
2. 在第 2 步点击“制作自己的附件”，开始一份**新草稿**；已有未保存调整时先保存，避免把切换新草稿当成继续编辑。选择“图片放在人物哪里”（前层、后层或前后双层），再点“选择或替换图片”，按界面位置选择透明 PNG。要继续修改旧附件则应从“继续编辑已有附件”打开，不要重新从同一 PNG 新建。原 PNG 留在原位置；保存时才复制进附件文件夹。帽子等双层素材分别选前、后 PNG，不把它们合成一张图。
3. 在第 3 步选择当前模型真实可用的“附件跟随位置”。需要在左侧直接移动图片时先看“开启拖动”是否已开启，再调偏移、大小和角度。换部位后仍要重新看位置；图片不应需要重选。播放与用途有关的动作，看附件是否持续跟随。左侧人物视图的移动、缩放和旋转只是查看方式，不应当作附件摆放参数保存。
4. 给附件填容易辨认的显示名，在第 4 步点击“保存附件”。等结果明确显示保存成功及路径，再到制作器资料库重开，确认图片、人物、部位和位置都恢复。想保留旧附件并做新款，可用“另存为新附件”；普通流程只填显示名称，系统自动生成新的目录及技术身份；高级配置 ID 无需修改。
5. 需要给游戏使用时，在制作器第 5 步选游戏，确认该游戏用配套 MyGO 引擎，按需复制人物，再点击“添加 / 更新到这个游戏”。完成后保持结果页可查，打开宿主 `release` 内的 `WebGAL_Terre.exe` 并进入这个游戏。在 Terre 的剧情列表搜索“附件测试”或附件名，按结果里的 `game/scene/附件测试-…txt` 精确选中**独立验证剧情**。按正常速度检查首次出现、动作跟随、前后遮挡和退出后的清理。正式剧情由你自己在 Terre 编辑器中编辑；可用“附件控制”“舞台实体控制”卡片，或切到脚本模式参照验证剧情填写命令。按钮旁会常驻提示“添加成功后会自动生成独立测试剧情，不会修改你的正式剧情。”成功结果显示实际文件名和完整路径；失败不会提示生成成功。

若保存成功但随后刷新列表失败，先查看保存结果中的路径和实际文件，不要连续点“另存”为了碰运气。把完整报错及 CMD 日志留给维护者。

### 3.1 先把 PNG 准备好

图片应有透明通道，主体周围的透明留白也属于**整张画布**。制作器默认以整张画布的中心作为图片支点，而非自动寻找可见像素的中心；所以同一顶帽子若在新图中被画到更靠左的位置，即使附件偏移没有变化，画面也会像“帽子移了位”。导入器还会检查图片尺寸和文件大小：单边不能超过 8192 像素、宽×高不能超过 16,777,216 像素，单层 PNG 不超过 8 MiB，前后两层文件合计不超过 8 MiB。超限时应调整图片本身，而不是删掉附件配置或安装记录。

前后双层**没有强制相同宽高**，但两层共用一组位置、缩放、旋转和画布支点，制作时推荐使用同尺寸画布，把同一个佩戴基准放在相同像素位置。例如一顶帽子的前帽檐和后帽身分别保存为透明 PNG，但都用相同的画布中心对准头部；本案例两张帽子图都是 995×363。若两层的主体在不同画布位置，普通工作台没有“只把前层右移”的独立摆放参数，须先在素材中对齐或重做分层。单层放在人物前方或后方只改变整层绘制顺序，不能自动让某一根手指压住花柄、让刘海局部遮住眼镜；这种模型内部遮挡超出本包普通前后层能力。

替换已有附件的一层 PNG 时，制作器保留原有位置、大小和角度数值，并重载该层图片；它不会根据新图的尺寸或透明留白替你重新校准。替换后先在工作台检查静止与相关动作，再保存附件、重开核对，并对已经添加的游戏重新执行“添加 / 更新到这个游戏”；旧游戏副本和旧导出成品不会自动同步。切换前层、后层、双层模式时也要检查**最终保存的层数和图片**，不要只凭工作台里曾经选过一张图推断它已随成品导出。

### 3.2 看懂摆放数值

| 工作台操作 | 实际改变什么 | 怎样判断做对了 |
| --- | --- | --- |
| 水平 / 垂直偏移 | 相对已选锚点的局部位置；未旋转的常见视图中，正 X 向右、正 Y 向下 | 先在静止姿态微调，再播相关动作；人物转动后，它不是固定的屏幕方向 |
| X / Y 大小 | 图片局部尺寸的正数倍率，`1` 是当前素材的局部原始倍率，不等于人物真实比例 | 比较附件与目标部位的相对大小，不要用预览窗口缩放值代替它 |
| 旋转 | 绕图片的统一画布支点旋转；工作台角度以度输入，脚本变换的旋转值以弧度表示 | 看佩戴边缘是否随动作自然转动；透明留白可能让视觉中心偏离支点 |
| 拖动附件 | 写入这件附件的局部摆放参数 | 先确认“开启拖动”，拖完再看右侧数值和保存后重开结果 |
| 平移 / 缩放 / 旋转左侧人物视图 | 改变你看画面的方式，不写入附件摆放 | 调整视图后，右侧摆放数值应保持；回到正常视图再判断佩戴效果 |

人物动作中的网格缩放如何传给附件，还受当前适配的缩放模式影响；因此“大小 1”只表示附件自身的倍率起点。若静止时合适、动作时明显漂移，先按第 7 节检查锚点和选点，再调整图片摆放；单纯反复改偏移往往只能修好一帧。

## 4. 把已有角色与服装立绘放进制作区

**快捷批量复制：**先按第 1 节运行安装后 `release/WebGAL-Attachment-Manager/02_打开附件制作器.cmd`，让制作区创建完成。用 Windows 文件管理器打开你已有 MyGO 游戏的 `game/figure/`，把需要的**整个角色文件夹**一次复制到所安装宿主的 `release/WebGAL-Attachment-Authoring/workspace/game/figure/`，保留每套服装的目录层级及共用动作、表情、贴图等依赖。比如原文件是 `游戏/game/figure/sakiko/casual-2023/model.json`，复制后应是 `release/WebGAL-Attachment-Authoring/workspace/game/figure/sakiko/casual-2023/model.json`。请**复制**，不要移动原游戏素材；目标位置已有同名文件夹时先核对内容，不直接覆盖。这条路径可一次处理多个人物和多套服装，免去在网页里逐套点击导入。

复制完成后回制作器，在第 1 步展开“锚点制作器（试用）：自定义部位 / 外观专属锚点”→“需要换另一套立绘时展开”，点击“刷新立绘列表”。制作器会扫描 `workspace/game/figure/` 下的 Cubism 2 模型入口 JSON（通常叫 `model.json`），并核对其引用的 `.moc`；已有可匹配锚点组的外观会进入上方“角色”→“服装 / 立绘”列表，选中后点击“载入所选立绘”。**出现在模型扫描结果中不等于已有可用锚点**：没有匹配锚点组的外观需在锚点制作器里选该模型，点“载入所选立绘（无需现成锚点）”，按第 7 节制作、保存并应用锚点。复制后仍要逐套检查立绘能正常显示、动作和表情资源齐全，不能只看文件夹名称或锚点同名就认定适配完成。

**使用页面按钮导入：**在第 1 步展开“导入自己的人物模型”，选择能覆盖 `model.json`、贴图、动作、表情等依赖的**完整来源文件夹**；一个角色的多套服装共用动作时，选它们共同的角色目录。然后在下拉框明确选本次要导入的一套模型入口，填写可读名称，点击“检查并复制到制作区”。该按钮每次处理选中的一套外观，并检查必要依赖；原模型留在原位置。成功提示会显示这套模型的 `game/figure/.../model.json` 路径；展开同一区域的“已导入人物与模型路径”也能再次查看。实际文件位于所安装宿主的 `release/WebGAL-Attachment-Authoring/workspace/` 加上提示中的相对路径，通常形如 `game/figure/人物名称/服装名称（导入-短标识）/model.json`。以界面显示的**实际路径**为准，不要自己猜短标识。这样无论采用批量复制还是按钮导入，都知道模型在制作区的哪里。不要把“资料库已有 Profile”理解成“模型文件已随插件提供”。

添加到游戏是另一步。在制作器第 5 步选目标游戏，查看“人物模型预检”：若显示“已就绪”，可继续添加附件并用独立验证剧情检查实际效果；若提示缺少模型文件，先回“导入自己的人物模型”区域展开“可选：将导入人物复制到游戏”，确认上方已选中并显示这套人物，点击“将当前导入人物复制到第 5 步所选游戏”，等复制完成再添加。制作区手动批量复制的模型也可按此方式复制到游戏。目标游戏已有同一路径的完整模型时，按预检结果处理，无需再次复制；“已就绪”主要表示必要文件存在，仍须核对游戏里的具体外观和动作。模型与 SDK 的使用及再分发权限由素材提供方决定。

## 5. 同一附件适配第二个人物或第二个部位

先在制作器中**打开已有附件**，不要从同一张 PNG 新建另一件。切换到第二人物及外观，或选择当前模型的另一有效锚点。工作台可能显示“未校准”的默认起点；此时原附件和图片仍是同一份，但新目标的位置需要你调整。调好后点击“保存附件”，再重开并分别切回两个目标核对。图片应仍只保存一份，原目标参数应保持。若界面没有恢复预期目标或报锚点/Profile 冲突，应停下查看诊断，不靠重复另存来制造新副本。

“锚点名称一样”不代表已经校准；不同 Profile、外观和网格需分别检查。若多套目标中有歧义或 Profile 不匹配，按界面提示明确选择或修正，不要用手改 ID 绕过。新增目标不是“另存为新附件”，除非你确实需要一件独立作品。

## 6. 导出附件文件夹、添加游戏与导出游戏成品

这三个“导出/添加”动作的目标不同。需要把一件附件作为文件分享或备份时，在制作器第 4 步展开“更多：复制与分享附件”，选择**导出完整附件文件夹**并在浏览器弹出的目录选择窗口选目标目录。成功后回到**刚才选的目录**，找到新建的附件子文件夹；结果提示可能只显示目录名，不给出完整绝对路径。确认子文件夹中有 `attachment.json`、`images/`、`manifest.json`、使用说明及必要配置；保留整个文件夹，不能只发 PNG。如果浏览器提示“当前浏览器不支持目录选择”，先保存附件，再按保存结果给出的路径，在文件管理器中复制**完整附件文件夹**。目标已有同名内容时先核对，不用覆盖来碰运气。导出文件夹不等于添加到游戏，也不自动改制作器资料库。

要在某个游戏里使用，先在制作器第 5 步选**那个实际游戏**，核对模型和锚点，再点“添加 / 更新到这个游戏”。制作器会给出目标位置与独立验证剧情。随后启动该宿主的 `WebGAL_Terre.exe`，打开同名游戏，在 Terre 剧情列表搜索“附件测试”或附件名，并按制作器结果里的 `game/scene/附件测试-…txt` 选中对应文件。正常播放确认人物、附件、动作、遮挡、退出和重播。只有这一步成功，才在 Terre 编辑器里打开自己的正式剧情，用“附件控制”“舞台实体控制”卡片，或脚本模式参照验证剧情填写命令；不要把独立验证剧情误认为正式剧情已被修改。制作区能预览不代表目标游戏已部署或 Runtime 已通过。

需要给玩家分发整个游戏时，启动宿主 `release/WebGAL_Terre.exe`，进入目标游戏，在游戏编辑器顶栏打开“导出”，选择“导出为网页”或“导出为可执行文件”。Windows 上成品通常分别在 Terre 用户数据目录的 `Exported_Games/<游戏名>/web/` 与 `Exported_Games/<游戏名>/electron-windows/`；后者的玩家入口是导出目录里的 `WebGAL.exe`，不要误点安装包 `payload` 下的 `WebGAL_Terre.exe`。在导出的正式 Runtime 再跑一次关键场景。网页导出后在 Windows 双击“启动游戏.cmd”，保持日志窗口打开。结束时点网页上方“结束游戏并关闭服务”，或双击“关闭本地服务.cmd”；网页部署仍使用index.html。file:///直开与HTTP(S)运行不同，详见第11节。不要把制作器导出的单件附件文件夹误当成可直接双击运行的完整游戏。

## 7. 自己制作锚点

已有锚点组的模型可以先按第 1 步载入；没有锚点组的自定义模型，应展开“锚点制作器（试用）：自定义部位 / 外观专属锚点”→“需要换另一套立绘时展开”，点“刷新立绘列表”，在“锚点制作目标立绘”选模型，再点“载入所选立绘（无需现成锚点）”。等左侧立绘完整出现，点击“为画面中的立绘新建锚点组”。先在“跟随网格”选相关网格；找不到时可用“在画面点击，查找附近网格”。再点“暂停并选点 / 重设参考姿态”，在同一网格点击至少三个分散且不共线的黄点，调整权重并为部位命名。点击“确认这个锚点到草稿”，再用“播放动作检查随动”检查几个相关动作；需要调整时回到选点与确认步骤。最后点击“保存锚点组到本地资料库”，再点击“用已保存锚点制作附件”。**只选点而没有确认到草稿，保存会失败。** 网格命名和制作流程可以离线完成；AI 仅可选辅助建议，不代替你对部位与动态效果的检查。

当前自建锚点主要支持已验证的 Cubism 2 路径，单锚点使用同一 drawable 的加权点。手掌翻转、模型内部遮挡和复杂握持并不会因为保存一个锚点而自动解决。自建锚点用于游戏时还需要配套版本的 Runtime。

### 7.1 先选会跟着目标部位运动的网格

在下拉框或“在画面点击，查找附近网格”中缩小候选后，逐个查看黄色顶点是否确实落在需要跟随的部位。头饰先找随头部整体运动的网格，耳饰找随目标耳部运动的网格，手持物找随目标手部运动的网格；**名称相近不是证据**，附近也可能有遮挡或其他图层的网格。先播放与用途相符的转头、举手等动作，观察该网格是否一直随目标运动，再暂停选点。案例实物中，祥子草帽的头部锚点使用 `D_PSD.43` 上五个点，祥子花的手部锚点使用 `D_PSD1.83` 上四个等权点，灯的左耳锚点使用 `D_PSD.155` 上五个点；这些网格编号只属于案例所带模型，不能照搬到另一套服装。

![同一网格内的锚点选点原理示意；此图不是实际模型截图](./图1_锚点选点原理示意.svg)

上图解释选点原则，**不是本包的实机截图或“照着点就一定正确”的模板**。先试 3～5 个围住实际佩戴区域、横纵方向都有间距的点；它们必须在**同一网格**上，不要挤成近乎一条直线，也不必为了覆盖整张网格而选到会独立扭曲的远处区域。实现允许 3～64 个不同顶点，权重必须是正的有限数。绿色十字是按权重算出的中心；首次尝试可让各点保持默认权重 `1`，权重会按总和参与计算，**不要求手工凑成总和 1**。若中心被不稳定点拉偏，先考虑换点，再考虑提高稳定点的相对权重；权重越大，该点对跟随中心和转向的影响越大，但不能代替正确网格。

### 7.2 参考姿态、确认和保存是三个状态

“暂停并选点 / 重设参考姿态”会把**当前暂停时看到的姿态**作为本次编辑的网格参考，不保证自动回到模型的中性姿态。若不希望抬手中途姿态成为基准，先把模型调到希望作为基准的姿态，再重新取样。重设或调整点后仍须重新“确认这个锚点到草稿”；已经保存的其他附件不会因你在页面上点了一下就自动重新校准。

| 你做到哪里 | 此时有什么 | 下一步和成功判断 |
| --- | --- | --- |
| 刚暂停并选择网格顶点 | 仅当前选点/参考姿态编辑状态 | 看点与绿色中心，再点“确认这个锚点到草稿” |
| 已确认到草稿 | 本次工作台草稿里有锚点定义，磁盘资料库尚未因此完成保存 | 播相关动作检查；满意后点“保存锚点组到本地资料库”并查看成功提示 |
| 已保存到本地资料库 | 本机制作区有 Profile；原来的 PNG 附件和已部署游戏不会自动更新 | 点“用已保存锚点制作附件”，调整该附件摆放，保存附件、重开核对，再添加/更新到游戏 |

### 7.3 用动作发现问题，再决定改哪一层

| 看到的现象 | 优先检查 | 最后再调整 |
| --- | --- | --- |
| 选点时就找不到目标部位 | 模型是否正确载入、当前 drawable 是否覆盖目标、是否选到遮挡网格 | 更换网格，而不是盲调 PNG 偏移 |
| 静止位置合适，但转头或举手后漂移/翻转 | 网格是否随该部位、点是否同一局部且不近共线、参考姿态是否取在合适时刻、权重中心是否偏离 | 校正图片偏移/角度；它不能修复错误网格 |
| 动作中跟随稳定，只是一直偏左、过大或角度不合 | 工作台里的水平/垂直偏移、大小、旋转和 PNG 留白 | 微调摆放，再保存、重开、重新部署 |
| 前层能看到，后层或手部遮挡不自然 | 实际所选层、前后两图的画布基准、目标模型的内部绘制关系 | 整理素材；本包的整层前后控制不能自动做模型内部逐部件遮挡 |

一个模型、一个动作上看着正确，只说明这个组合。制作头、耳、手等锚点时，应各看至少一个真正会让该部位移动的动作，并在独立验证剧情和正式游戏里再次判断。图示用于理解方法；本说明里的两张原理图不是本版实测界面的截图或动图。

## 8. 检查、备份和迁移

- 附件资料库在所安装宿主的 `WebGAL-Attachment-Authoring/workspace/game/attachments-v2/portable/`。一个完整附件文件夹至少有 `attachment.json`、`images/`、`manifest.json` 和说明；备份或分享时复制**整个文件夹**，不要只复制 PNG。
- 原始 PNG 和原始人物模型不因制作附件而移动或删除。制作区、目标游戏以及导出成品是不同副本；修改其中一处不会自动同步所有位置。
- 用户可以手工编辑自己的图片和参数。Creator 重新打开时若提示外部变化，应先检查差异，再决定接受当前文件并重建基线；不要删除 manifest 或安装记录来消除提示。
- 解压包根目录的 `01_安装或升级.cmd` 用于安装或升级；安装后的 `release/WebGAL-Attachment-Manager/` 中，`02_打开附件制作器.cmd` 打开制作器、`03_验证安装.cmd` 检查安装状态、`04_修复安装.cmd` 尝试受管修复、`05_停止附件服务.cmd` 停止制作器服务、`06_卸载插件.cmd` 卸载受管部分并保留用户内容。使用 `WebGAL_Terre.exe` 时，要点宿主 `release` 根目录的程序，**不要点安装包 `payload` 内用于安装的同名 EXE**。卸载前仍建议自行备份重要作品。
- 完整附件文件夹可复制；已安装 Terre、整个游戏或安装身份的随意复制/改名另有路径和归属限制，不能按“附件可复制”推断整台宿主也能无提示搬家。

### 8.1 接收别人分享的完整附件并继续编辑

分享者发送导出的完整附件文件夹，并注明具体版本、目标模型相对路径、服装/Profile及已校准部位。附件不包含人物模型本体；只发PNG或剧情命令不够。

1. 先备份自己的制作区与收到的原件。核对attachment.json、images、manifest.json和使用说明齐全。把整个附件目录按原名复制到制作区workspace/game/attachments-v2/portable/，同名目录或同ID冲突时停止，不覆盖。
2. 按模型导入流程准备结构兼容的完整人物，核对附件记录的相对模型路径与所选外观。目录相似、导入成功或同名锚点不等于适配匹配；路径冲突时检查适配，不改模型或技术ID绕过。
3. 在制作器载入人物，从附件列表选择收到的作品并点击载入。有效外来目录首次会提示登记本机编辑权限；取消保持磁盘和原草稿，确认登记只建立本机记录，保留图片、参数和稳定ID。
4. 核对图片、适配与摆放，修改后点击保存附件；重新载入核对参数。原分享目录保持不变。若附件内容已手改，先查看差异提示并明确接受；过期或损坏内容不可用反复覆盖绕过。
5. 需要使用时再添加到自己的游戏，在独立验证剧情和正式Runtime检查；本机登记或列表出现都不等于游戏部署成功。

MYGO321-LOCAL-WEB-REPAIR.3已完成隔离接收者的取消、登记、修改保存与重载检查。未承诺自动迁移不兼容人物适配，也不提供绕过重复ID或文件冲突的接管。

### 8.2 备份与换电脑：分别保留作品、锚点、模型和游戏

| 需要保留的东西 | 当前通常所在位置 | 单件“导出完整附件文件夹”是否包含 |
| --- | --- | --- |
| 已保存附件和多人物适配 | `release/WebGAL-Attachment-Authoring/workspace/game/attachments-v2/portable/` | **包含所导出的那一件**及其内嵌适配/Profile 快照，不包含资料库里的其他作品 |
| 自建锚点/Profile 资料库 | `release/WebGAL-Attachment-Authoring/library/model-profiles/` | **不包含独立资料库文件**；不要把内嵌快照当作已恢复整个锚点库 |
| 制作区模型与导入记录 | `release/WebGAL-Attachment-Authoring/workspace/`，模型通常在 `game/figure/` | **不包含模型**；需连同贴图、动作、表情和依赖保留 |
| 目标游戏剧情、人物和已添加附件 | 当前 Terre 用户数据中的对应游戏目录，通常在 `%USERPROFILE%\.webgal_terre\games\<游戏名>\` | 不包含；单件导出也不是整个游戏备份 |
| 已导出的玩家成品 | Terre 的 `Exported_Games/<游戏名>/` | 不包含；要保留旧网页/EXE 时另存 |

做整机备份时，先停止制作器服务、退出 Terre，分别复制完整 `workspace/`、`library/` 和要保留的游戏目录到备份盘，记录安装包修订及原路径；再抽查附件目录、Profile 文件、模型入口和剧情文件确实存在于备份中。**不要只备份 `portable/` 就删掉旧电脑资料。** 原始 PNG 若将来还要重新作图，也应另行保存。

换电脑或更换安装路径时，先在新环境用相同适配版本完成干净安装，并保留旧电脑与备份不动；把恢复工作先放在**新环境的隔离测试副本**，按上表核对同名目录和路径，再尝试载入一件附件、检查 Profile/模型、部署到测试游戏、正常播放验证剧情。当前版本对整个已安装宿主、绑定游戏及受管身份的跨机器复制/改名**没有一条已经验收的无冲突一键恢复路线**；若碰到 ownership 或绝对路径冲突，应停止写入并提供备份与错误给维护者，不能通过删安装记录、改 manifest 或覆盖同名游戏继续。旧环境在新环境验收前不要清理。

### 8.3 修改以后，哪个副本会更新

![原素材、制作区、目标游戏和玩家成品的副本流向](./图2_资料与游戏副本流向.svg)

| 你改的是 | 已经改变的地方 | 要让后续副本得到修改，还要做什么 |
| --- | --- | --- |
| 原始 PNG 或原始模型目录 | 只有原始素材 | 在制作器里重新选择/导入对应素材，检查后保存附件；已保存作品不会自动读取原目录的新字节 |
| 制作器工作台上的图片、锚点或摆放草稿 | 当前网页草稿 | 明确“确认到草稿”（锚点）、保存 Profile/附件，并从资料库重开核对 |
| 已保存附件的 PNG 或适配 | 制作区的那一件作品 | 若目标游戏需要新版本，再执行“添加 / 更新到这个游戏”，核对冲突和验证剧情 |
| 目标游戏中自己的剧情或手工调整 | 该游戏副本 | 制作区不会自动反向吸收这些改动；再次添加时先检查游戏内文件的归属和冲突，不假设可直接覆盖 |
| 游戏编辑器里的正式剧情或资源 | 当前游戏 | 再从 Terre 导出新网页/EXE，并在新成品中重跑关键场景；旧导出成品不会自动变更 |

改名、另存、移除也按“显示名称、配置 ID、资料库原件、游戏副本”分别判断。修改**显示名称**不应被当成改剧情引用的配置 ID；手改技术目录、配置 ID 或直接删 `portable/` 文件夹可能让旧剧情找不到附件。另存为独立作品会生成新身份并保留原件，成功后仍应核对新旧文件夹；把制作区原件移走不等于已部署游戏和旧玩家成品随之删除。要清理作品，先查哪些剧情还引用它、保留备份，再分别处理各副本。对已在游戏内手工改过的受管文件，再次添加如提示冲突，应先保护手工修改并按提示处理，不用覆盖来消除报错。

## 9. 剧情命令：作用、写法和相互影响

最稳妥的入门方法是：在制作器把附件**添加到游戏**后，打开它生成的独立验证剧情，从中复制实际的 `-config`、`-profile`、`-anchor`、立绘键和附件 ID，再改编自己的剧情。不要照抄下文的示意 ID，也不要凭人物中文名猜技术身份。每条 WebGAL 剧情命令以分号结束；参数名、动作名和 JSON 字段需要保留程序规定的英文拼写。

本插件给剧情脚本增加两组命令：`attachment` 四种动作、`stageEntity` 五种动作；原有 `setTransform` 和 `setTempAnimation` 也可把附件实体作为目标。以下是**本包的附件脚本命令合同**，并非把所有 MyGO/WebGAL 原生命令重新列一遍。Terre 中若有对应可视化卡片，可先用卡片生成，再对照生成的脚本检查身份与顺序。第 9.6 节逐项标明这些命令在林间演示里是否实际出现。

### 9.1 命令中的身份

| 参数 | 应填什么 | 何时需要 |
| --- | --- | --- |
| `-figure` | 当前剧情里已经载入的**立绘键**，例如 `fig-center`，不是人物显示名或模型路径 | `attachment` 全部动作、`stageEntity:reattach` |
| `-id` | 该立绘下这一次附件的本地实例名，例如 `hat` | `attachment` 全部动作 |
| `-entity` | 一次舞台附件的稳定实体名，例如 `hat-01`；分离、自由移动、跨人物重绑仍沿用它 | `attachment:add` 建议明确给出；`stageEntity` 全部动作必需 |
| `-config` | 已添加到**当前游戏**的附件配置 ID，以制作器结果或验证剧情为准 | `attachment:add` 必需 |
| `-profile` | 目标立绘实际使用的锚点配置 ID。多 Profile 或跨人物时应明确写 | `attachment:add`、`stageEntity:reattach` 可选但常有必要 |
| `-anchor` | 目标 Profile 内确实存在的语义锚点技术名，例如 `head`、`ear-left` 或自建锚点 ID | `attachment:add`、`stageEntity:reattach`；省略时默认 `head`，不表示任何模型都有它 |
| `-slot` | 同一立绘上的命名槽位；两个不同附件写同一槽位名会报冲突，系统不判断图片在画面上是否重叠 | `attachment:add` 可选；同名槽位被占用会报冲突 |

#### 用 Terre 图形卡片生成命令

先打开目标游戏的正式剧情，切到“图形编辑器”，在底部点击“添加语句”→“附件控制”；新增卡片若只显示标题，点标题旁的小三角展开。动作选“添加附件”，把“目标立绘 ID”填为此前 `changeFigure -id` 指定的立绘键；“附件实例 ID”填本地名，对应命令的 `-id`；“稳定实体 ID”填后续分离和转移都要沿用的名字，对应 `-entity`。在“附件配置 preset”选择当前游戏的附件配置；若选到 `portable/<文件夹>/attachment.json`，生成脚本里的 `-config` 会是 `v2/<文件夹>`，不要把 Windows 绝对路径直接填进剧情。再按制作器验证剧情核对“模型适配 Profile”“语义锚点”，必要时填“附件槽位”“过渡时间”“缓动类型”。例如第 9.10 节草帽练习会得到以下这一类命令：

```webgal
attachment:add -figure=learn-sakiko -id=hat -entity=learn-hat -config=v2/夏日捉虫小祥的草帽-ffxmd2 -profile=user-profile-79d85c2b-c03c-4278-8efa-ccc3d60a0f09 -anchor=head -duration=1;
```

要处理已经出现的附件，在同一“添加语句”位置选“舞台实体控制”，选“分离”“重新附着”“隐藏”“显示”或“移除”，把“实体 ID”填成上面 `-entity` 的值；重新附着还要填目标立绘、Profile 和锚点。“继续执行后续语句”对应 `-continue`，只在该操作完成后确实需要自动续句时勾选；不要给上面的 `attachment:add` 再手写 `-continue`。卡片生成后切到脚本视图，检查生成的 `-figure/-id/-entity/-config/-profile/-anchor` 是否对应**当前游戏和当前立绘**；长命令在编辑器中可能自动折为多行，不表示多条命令。若找不到上述卡片，先核对当前 Terre 与游戏实际使用的是第 1 节指定的宿主和引擎。这是按冻结版本的卡片源码核对的操作路径，真实界面截图尚未采集。

先用游戏已有的立绘命令把目标 Live2D 人物载入，再执行 `attachment:add`。只有外观名称相同、PNG 相同或锚点文字相同，都不能替代真实模型/Profile/配置匹配。人物换装、替换、退场或场景重放后要重新检查附件实例与目标立绘，不能假设旧实体仍绑定在新人物上。

### 9.2 `attachment`：以立绘和本地实例名操作

| 命令 | 效果 | 必要参数和常用可选参数 |
| --- | --- | --- |
| `attachment:add` | 发起附件加载；目标 Live2D 立绘、资源、Profile 和锚点可用后显示，可按指定时长淡入；**剧情下一句不因此等待加载完成** | 必需 `-figure`、`-id`、`-config`；建议明确 `-entity`、`-profile`、`-anchor`；可用 `-slot`、`-duration`、`-ease` |
| `attachment:hide` | 保留附件实例和绑定，隐藏它；以后可再 `show` | 必需 `-figure`、`-id`；可用 `-duration`、`-ease` |
| `attachment:show` | 显示先前隐藏的同一实例，不新建另一份图片 | 必需 `-figure`、`-id`；可用 `-duration`、`-ease` |
| `attachment:remove` | 移除该附件实例；以后再出现需要重新 `add` | 必需 `-figure`、`-id`；可用 `-duration`、`-ease` |

以下四行分别展示**各动作的写法**，不是可直接连续粘贴的剧情；若原样排在一起，`attachment` 的自动继续会让它们很快依次执行，最后把附件移除。`-config`、`-profile`、`-anchor` 和立绘键必须换成**你的验证剧情**里的实际值：

```webgal
attachment:add -figure=fig-center -id=hat -entity=hat-01 -config=v2/你的附件配置ID -profile=你的ProfileID -anchor=head -slot=headwear -duration=500 -ease=easeInOut;
attachment:hide -figure=fig-center -id=hat -duration=0;
attachment:show -figure=fig-center -id=hat -duration=500;
attachment:remove -figure=fig-center -id=hat -duration=0;
```

`attachment:add` 默认过渡约 500 毫秒；这组兼容命令的 `hide/show/remove` 未写 `-duration` 时默认为瞬时。显隐或移除需要瞬时效果时可明确写 `-duration=0`，需要可见过渡就写时长；**添加附件的 `0` 还有下面所述的首帧监督差异**。`attachment` 命令在解析时具有**自动继续下一句**的旧兼容语义，不能靠手写 `-next=false` 把它变成人工停顿，也不要额外加 `-continue` 造成多推进。若下一句依赖附件真实首帧或分离前位置，可在两者之间安排可见的剧情检查点，并以正常播放验证。`add -duration=0` 只是无淡入，不保证模型和图片加载也瞬时完成；加载失败或超时会有诊断。

第 9.10 节两段练习使用的 `-duration=1`，单位是**毫秒**。这里的 1 毫秒不是为了让观众看清淡入，而是让添加操作进入正时长的资源、淡入和有效首帧监督路径；在正常可渲染条件下，用户不能手动点击抢过这个监督过程。设为 `0` 会走瞬时添加路径，没有这项首帧监督。**两种写法都会自动推进到紧邻的下一句**，因此 `1` 也不能充当自动连续剧情的完成屏障；页面或附件暂时不可渲染时，监督还可能延期结束。不要因视觉上都接近瞬时，就把练习里的 `1` 随手改为 `0`。

### 9.3 `stageEntity`：以同一个实体名操作

| 命令 | 效果 | 必要参数和常用可选参数 |
| --- | --- | --- |
| `stageEntity:detach` | 从人物锚点解绑，按**实际可用渲染帧**捕获位置、可见性等，使同一实体成为舞台自由附件；之后人物移动不应把它带走 | 必需 `-entity`；可选 `-coordinates=figure`（默认）或 `world` |
| `stageEntity:reattach` | 将自由附件按时长移到指定人物锚点，完成后恢复附着；原实体及附件配置身份保持 | 必需 `-entity`、目标 `-figure`；常用 `-profile`、`-anchor`、`-duration`、`-ease` |
| `stageEntity:hide` | 隐藏这个实体，仍保留它，适用于已附着或自由状态 | 必需 `-entity`；可用 `-duration`、`-ease` |
| `stageEntity:show` | 显示这个实体，不新建另一份 | 必需 `-entity`；可用 `-duration`、`-ease` |
| `stageEntity:remove` | 完全移除这个实体；包含它可能处于的自由状态 | 必需 `-entity`；可用 `-duration`、`-ease` |

下面是需要逐步检查的示意流程；若 `detach`、自由移动或返程后希望自动进入下一句，按实际剧情为相应异步命令写 `-continue`。`hat-01` 必须和前面的 `attachment:add -entity=hat-01` 完全一致：

```webgal
stageEntity:detach -entity=hat-01 -coordinates=figure;
setTransform:{"position":{"x":120,"y":-80},"rotation":0.3} -target=hat-01 -duration=800 -ease=easeInOut;
stageEntity:reattach -entity=hat-01 -figure=fig-center -profile=你的ProfileID -anchor=head -duration=800 -ease=easeInOut;
stageEntity:remove -entity=hat-01 -duration=0;
```

`detach` 默认的 `figure` 坐标保留当帧世界位置，同时把该人物原生布局原点冻结为自由附件后续位置参数的参考；`world` 是兼容旧脚本的舞台绝对坐标，`(0,0)` 参照舞台左上角。`detach` 本身只解除绑定并抓取姿态，**不会让附件飞走**；自由飞行需随后对同一个 `-entity` 写 `setTransform`，给 `detach` 添加 `-duration` 不会产生飞行动画。不要把 `figure` 模式下的数值当作网页预览窗口的 CSS 像素，或把每个立绘的 `(0,0)` 都当屏幕中心。自由附件的 `setTransform` 位置是**目标值**，不是在当前值上累加的增量。重新绑定会继续使用同一实体可恢复的附着局部状态；若先前对它做过局部位移、旋转或透明度动画，**不能假定 reattach 自动回到 Creator 保存的初始摆放**。需要清除前面动画的局部扰动时，应明确恢复相应数值，或像第 10 节草帽案例那样先移除旧运行实例，再从保存配置重新 `add`。

`stageEntity:show/hide` 默认约 500 毫秒，`stageEntity:remove` 默认瞬时，`stageEntity:reattach` 默认约 500 毫秒。`detach` 和 `reattach` 是需等待真实状态的异步操作，**不能用 `-next`**；要在操作成功结束后自动进入下一句，可用 `-continue`。`show/hide/remove` 若设了可见过渡，也可用 `-continue` 在过渡结束后续句；`-next` 只让下一句立即进入，不等过渡。不写 `-continue` 时，适合留一个人工检查点。显式 `-space` 不受支持，附着/自由坐标空间由实体状态决定。目标人物尚未准备好、Profile 或锚点不匹配，或者目标人物的同一 `slot` 已由别的附件占用时，应观察错误，不要用大量固定等待或直接再 `add` 掩盖失败。自建锚点 ID 必须精确匹配，不是只要通过语法检查就能绑定。自由附件被 `remove` 后不能再 `reattach`，需要重新 `add`。

### 9.4 `setTransform` 与人物、附件状态的关系

`setTransform` 是 MyGO/WebGAL 的变换命令；本插件允许 `-target=实体名` 指向附件实体。示例 JSON 的 `position.x/y` 控制目标位置，`scale.x/y` 控制两轴缩放，`rotation` 使用**弧度**，`alpha` 控制透明度（0 为全透明，1 为不透明）；`-duration` 为毫秒、`-ease` 指定缓动，`-duration=0` 表示瞬时。具体效果还取决于附件是附着还是自由状态：附着时按锚点及局部参数运作；分离后按上段的自由坐标模式运作。同一实体的动画与重新绑定飞行若同时发生，可能相互覆盖或取消，按有依赖的顺序写并在实际剧情里观察。若命令写 `-target=人物立绘键`，改变的是人物，附着附件随父体走；`-target=附件实体名` 才改变附件本身。

同一镜头中对**人物**和**附件**分别写 `setTransform`，不意味着两条命令会天然以同一帧率同步。附着附件应跟随其父人物的最终帧；自由附件不会随父人物移动。对人物使用 `changeFigure`、动作或替换时，不要把“命令已开始”当成 Live2D 动作已到终态。特别是“动作后立刻 detach”，应在正常速度检查抓取的姿态。浏览器预览和网页成品曾有卡顿与末尾跳变反馈，见第 11 节；不能仅凭快进或单环境判定正式演出效果。附件实体的 JSON 变换只支持可映射的字段，不能把人物用的全部滤镜、mask 或旧动画字段直接套到附件上。

### 9.5 `setTempAnimation`：让附件执行多段临时动画

这是 MyGO/WebGAL 原有的临时动画命令，本包可用附件实体名作为目标。下例只展示两帧摇动的**写法示意**；第 10.3 节演示脚本中的草帽命令有七帧，完整数值以案例脚本为准：

```webgal
setTempAnimation:[{"position":{"x":0,"y":0},"rotation":0,"duration":0,"ease":"easeInOut"},{"position":{"x":-7,"y":-2},"rotation":-0.04,"duration":240,"ease":"easeInOut"}] -target=hat-01 -continue;
```

`-target` 必须是此前已创建的实体名，不能填附件显示名。数组按顺序给每段位置、旋转和时长；附件目标常用 `position.x/y`、`scale.x/y`、`rotation`、`alpha`，每帧还可写 `duration`、`ease`。实现另映射 `skew.x/y` 及部分外观字段，但**不是**人物动画所有滤镜字段都能用在附件上；复杂字段先用该版本的验证剧情定向检查。默认没有 `-keep` 时，动画结束会把**最后一帧**写入实体效果状态，不会自动回到校准原位。只在后续 `setTransform` 中写 `rotation` 时，位置、大小及透明度等未写字段仍保留当前值；需要以变换基准重设可用进阶选项 `-writeDefault`，但它也不是“重新从 Creator 载入整件附件”。

这类摇晃不会创建、分离或转移附件。演示中草帽摇晃时仍绑定在祥子头部；后面又写了把帽子移到画外的变换，并在返场前移除旧实例、重新 `add`，以清掉前一段留下的局部变换。连续动画、普通变换和重新绑定若作用于同一实体，应按依赖顺序安排，避免相互取消或覆盖。演示脚本使用了该临时动画的附件目标路径，实际画面还应正常播放核对；其他 MyGO 原生动画命令和复杂动画组合也不能由这一例推断为已完成视觉验收。

### 9.6 本案例实际覆盖了哪些附件脚本能力

| 命令或能力 | 本案例是否使用 | 在哪里、还缺什么 |
| --- | --- | --- |
| `attachment:add` | 使用 | 画外创建草帽与花；草帽被移除后再创建一次 |
| `attachment:hide`、`attachment:show` | **未使用** | 案例用实体名操作的 `stageEntity:hide/show` 实现花的藏起与亮出；第 9.2 节已给出这两种旧式写法 |
| `attachment:remove` | 使用 | 开场清理可能遗留的本地实例 |
| `stageEntity:detach`、`stageEntity:reattach` | 使用 | 草帽先分离再戴回，花从祥子手部转到灯左耳 |
| `stageEntity:hide`、`stageEntity:show`、`stageEntity:remove` | 使用 | 花的预先隐藏与举花、帽子淡隐后隐藏、退场清理 |
| `setTransform` 作用于附件实体 | 使用 | 仍附着的草帽画外淡隐，以及分离后的自由帽返场 |
| `setTempAnimation` 作用于附件实体 | 使用 | 草帽的多段摇晃；这是原有动画命令的附件目标用法，不计入上面九种新增动作 |

所以，**九种新增动作已在第 9.2、9.3 节全部列出，但演示剧情只实际使用其中七种**。它也没有覆盖所有参数与运行情境：例如 `-slot` 冲突、`-coordinates=world`、非零时长的隐藏/显示、存档恢复和快进后状态，都需要各自检查。示例展示的效果不等于这些未用路径已经通过真实游戏验收。

### 9.7 顺序、保存与重播的最小检查

1. 同一场景先载入目标 Live2D 立绘，再 `attachment:add`；检查首次出现及资源错误，再做 `hide/show`、变换或分离。
2. `-next` 常用于连续收集命令或并行动作，**不是“等待上一条动画结束”**。`stageEntity:detach/reattach` 明确拒绝它；需要成功结束后继续时用 `-continue`。`-duration=0` 才是明确瞬时。不要用这些参数替代目标立绘与模型就绪检查。
3. `hide` 保留实例，`remove` 删除实例；`detach` 保留同一实体但使它自由，`reattach` 再绑定。跨人物转移应保持同一个 `-entity` 和 `-config`，并在目标人物有对应锚点和适配时明确 `-figure/-profile/-anchor`，不要把花等道具复制成两件来模拟转移。
   日常显隐和移除，尤其分离或跨人物重绑后，优先用原 `-entity` 的 `stageEntity:show/hide/remove`。冻结源码仍保留了最初 `(figure,id)` 到实体的别名映射，因此第 10 节开场的已知来源清理可用原 `attachment:remove`；具体边界见第 9.9 节，不要再次 `attachment:add` 制造身份冲突。
4. 完整跑一次正式速度，再重播并检查重复实例、旧位置、透明度、层级残留。若剧情使用存读档或跳转，要分别从保存点和跳转目标核对当前附着/自由/隐藏状态；一次静态截图不能证明动画连续性。
5. 前后层附件会按当前人物与附件层级排序。自由附件从来源人物脱离后，邻近的其他立绘若使用非常接近的自定义小数 `zIndex`，飞行期间可能出现意外遮挡；需要在目标剧情实看顺序，不用固定 `+0.001` 的内部细节推算所有场景都会正确。

### 9.8 校准、脚本变换、显隐与自动推进

| 问题 | 本包的规则 | 编排时要做什么 |
| --- | --- | --- |
| 制作器已调好位置，脚本再写 `position:{"x":0,"y":0}`、`scale:{"x":1,"y":1}` | 对**附着**附件，这是本次舞台实例的额外变换起点；已保存的锚点和适配摆放仍参与绘制，不会凭这两个值跳回未经校准的模型原点 | 用独立验证剧情的实际身份试播；分离后位置改按第 9.3 节的自由坐标解释 |
| 只写 `rotation` 或 `alpha` | 附件变换按字段合并；未写的 `position`、`scale` 等保留当前值，`position.x/y` 与 `scale.x/y` 也可分别保留 | 不要以为“只写旋转”会清掉上一次的画外位置；需要复位时明确处理相应字段或重建实例 |
| `hide/show` 与 `alpha` 有什么区别 | `hide/show` 改**逻辑可见性**，淡入淡出是过渡系数；`alpha` 是实体自身透明度，二者互不自动重置 | `alpha=0` 后单独 `show` 仍可能全透明；先把 `alpha` 调回所需值，再 `show`。`hide` 也不抹掉此前的位置和透明度 |
| 多段临时动画结束后怎样 | 默认无 `-keep` 的 `setTempAnimation` 会把末帧写入实体效果状态，`reattach` 也不保证清除之前的局部扰动 | 若下一幕需要干净的保存状态，先明确复位，或像草帽案例一样移除旧实例并重新 `add`；`-writeDefault` 是高级变换基线选项，不是完整附件重新导入 |

“命令推进”“资源已就绪”“动画到终点”是三个不同事件：

| 命令组 | 下一句如何推进 | 能否当作自动连续剧情的完成屏障 |
| --- | --- | --- |
| `attachment:add` | 旧兼容解析默认立即自动推进；正时长在正常可渲染条件下监督资源与首个有效姿态，并防止用户手动点击抢过监督过程 | **下一句可能先于添加操作完成而开始**；`-duration=1` 也不是自动串接屏障，且不可渲染时监督可能延期结束 |
| `attachment:hide/show/remove` | 旧兼容命令默认自动进入下一句，`-duration=0` 是瞬时显隐/移除 | 可用于基础显隐，不应把非零时长过渡误当成自动等待 |
| `stageEntity:detach/reattach` | 不接受 `-next`；成功完成后可用 `-continue` 自动进下一句，失败时不会按成功路径继续 | 这是需要真实实体/目标状态的异步步骤；后续命令依赖它时，按该规则编排 |
| `stageEntity:hide/show/remove` | `-next` 立即向后进入；需要过渡完成后续句时用 `-continue` | 先区分“开始隐藏”与“已经隐藏/移除”，再安排依赖命令 |
| `setTransform`、`setTempAnimation` | 可用 `-next` 并行动作，或按剧情需要用 `-continue` 在动画结束后续句 | 同一实体上的下一段动画、分离或重绑应避免抢占/取消前一段 |

逐步点击时插入对白或人工检查点，有助于**人观察**草帽和花；录屏或自动连续演出不能把“有人看了一眼”当成程序同步。资源失败、目标不存在或操作被取消时应以运行结果和错误提示为准，不用固定等待秒数假装操作成功。

**不插对白，创建后立即分离、移动、重新附着：当前仍待整段实播验证。**冻结源码显示，紧邻 `attachment:add` 的下一句可先开始执行；`stageEntity:detach` 会等待目标附件物化和真实有效姿态，成功分离后才由它的 `-continue` 续句。接着自由移动与重新附着也可各自完成后续句。因此等待点应是 `detach` 的真实状态检查，不能把 `add -duration=1` 或人为停几百毫秒当作等待点。现有定向测试验证了添加的两条分支和分离等待有效帧，但**没有完成“add→detach→飞行→reattach”连续剧情的正常播放验收**；本版说明不把任何全自动片段标为已经验证可直接照用。正式剧情若要省掉人工检查点，应先在独立测试场景从头正常播放、重播，并观察首次姿态、分离坐标、飞行终点和重绑结果，再用于自己的作品。

### 9.9 换装、离场、存档与案例开场清理

下表把**源码状态规则**和**已有验证层级**分开。它不是“所有场景都已经在 Terre 和独立成品试播通过”的声明。

| 操作 | 附着附件 / 自由附件的预期 | 隐藏与恢复 | 当前证据边界 |
| --- | --- | --- | --- |
| 同一模型播放动作或表情 | 附着实例按该模型最终帧跟随；已分离的自由实例不再跟着人物走 | 逻辑可见状态应保持 | 源码合同与案例脚本静态覆盖；未逐项重播画面 |
| 同一立绘键换服装或替换模型 | 旧人物渲染代际会退役，再按当前舞台声明尝试匹配新模型/Profile；不兼容时应出现诊断，不能保证仍佩戴正确 | 不把“角色名字相同”当作隐藏状态或适配已正确迁移 | 源码路径已核；该换装组合未在案例中逐项验收 |
| 人物退场或重进 | 附着实例依赖对应人物；自由实例不再随原人物移动，但场景重置可清掉舞台实体 | 进入新场景前应按自己的剧情显式建立所需状态 | 不承诺所有 `changeFigure`/退场选项都保持同一实例；正式剧情需分别试播 |
| 存档并读档 | 实现记录附着/自由、坐标、透明度、可见性和原始别名，并在恢复时校验 | 隐藏标志属于保存状态，但资源或目标失配仍可能报错 | 源码有持久化路径；未对本资料包单独做存读档 GUI 回归 |
| 从中段“执行到此句”或快进跨过动作 | 不能指望被跳过的 `add`、动作终态或 detach 捕获姿态自动重建成从头正常播放的结果 | 以正常播放为摆放验收基准 | 用户已报告快进下 reattach 等待与 detach 中途姿态差异；见第 11 节 |

第 10.1 节开场的三条 `attachment:remove -figure=... -id=...` 是**防已知旧实例残留**：冻结实现会保留最初 `(figure,id)` 指向实体的别名，因此即使花已从祥子手部 `detach` 或重绑到灯，原来的“祥子 + flower”仍可找到该实体；该别名不存在时，`attachment:remove` 静默跳过。相反，直接对不存在的实体写 `stageEntity:remove` 会报 `ENTITY_NOT_FOUND`，所以不能仅凭命令名把开场三条机械替换掉。日常精确操作仍推荐 `-entity`；上述解释是源码静态核对，演示脚本的各种中断点尚未逐一实播验证。

### 10.1 `forest-00`：画外准备

**第一组：先处理可能遗留的帽和花。**

```webgal
attachment:remove -figure=forest-sakiko -id=hat -duration=0 -next;
attachment:remove -figure=forest-sakiko -id=flower -duration=0 -next;
attachment:remove -figure=forest-tomori -id=flower -duration=0 -next;
```

这三句分别尝试清理祥子身上的帽、祥子手上的花和灯身上的花。花可能在前一次播放中已经转到灯耳边，因此同时照顾两个归属。这里的清理是开场防残留，不是让玩家看见三次摘取动作；零时长使其瞬时完成。

**第二组：建立森林背景及初始画幅。**

```webgal
changeBg:forest-demo.png -next;
setTransform:{"position":{"x":0,"y":0},"scale":{"x":1.12,"y":1.12},"blur":0} -target=bg-main -duration=0 -ease=easeInOut -next;
```

第一句从 `game/background/` 读入森林图；第二句把背景放在初始位置并设为 1.12 倍缩放。目标是背景 `bg-main`，不是任何人物或附件。零时长用于先把场景摆好，后面才开始可见的入场。

**第三组：把三层人物画面先放在画外。**

```webgal
changeFigure:tomori/casual-2023/model.json -id=forest-tomori -motion=tomori/idle01 -expression=tomori/smile01 -duration=0 -zIndex=2.0005 -transform={"position":{"x":-1850,"y":0},"scale":{"x":1,"y":1}} -next;
changeFigure:sakiko/夏装捉虫小祥-捕虫网/model.json -id=forest-net -transform={"position":{"x":-2450,"y":-350},"scale":{"x":2.5,"y":2.5}} -duration=0 -motion=sakiko/smile02 -expression=sakiko/default -zIndex=1 -next;
changeFigure:sakiko/夏装捉虫小祥/model.json -id=forest-sakiko -motion=sakiko/smile02 -expression=sakiko/default -duration=0 -zIndex=2 -transform={"position":{"x":-2450,"y":0},"scale":{"x":1,"y":1}} -next;
```

灯、捕虫网层、祥子本体分别有自己的立绘身份。负的较大横坐标把它们置于画面左外侧；网兜层比祥子本体放大，并在纵向错开，以便两层在后续镜头里对齐。三条语句分别载入模型，不能把 `forest-net` 当作一张附件 PNG；以后祥子移动时，网兜也要有自己的移动命令。

**第四组：把草帽放到祥子头部。**

```webgal
attachment:add -figure=forest-sakiko -id=hat -entity=forest-hat -config=v2/夏日捉虫小祥的草帽-ffxmd2 -profile=user-profile-79d85c2b-c03c-4278-8efa-ccc3d60a0f09 -anchor=head -duration=1;
setTransform:{"position":{"x":-2450,"y":0},"scale":{"x":1,"y":1}} -target=forest-sakiko -duration=0 -ease=easeInOut -next;
```

第一句把已保存的草帽配置绑定到祥子的头部锚点，舞台实体名是 `forest-hat`。`-config` 找附件配置，`-profile` 找这套外观的锚点组，`-anchor` 指具体头部；这三个值必须与保存的附件和当前模型匹配。第二句再次确认祥子仍在画外，避免附件刚建好时人物尚未处于预期位置。草帽随祥子头部走，但草帽自身也是后面可以单独操作的实体。

**第五组：预先创建花，随即藏起。**

```webgal
attachment:add -figure=forest-sakiko -id=flower -entity=forest-flower -config=v2/祥子手上的花-dvq9ua -profile=user-profile-fd5ed25f-94d3-493b-aa62-74731daa3171 -anchor=user.a-7d1bc490-a22a-44e3-becb-d015e9cdfc4f -duration=1;
setTransform:{"position":{"x":-2450,"y":0},"scale":{"x":1,"y":1}} -target=forest-sakiko -duration=0 -ease=easeInOut;
stageEntity:hide -entity=forest-flower -duration=0;
```

花一开始就附着在祥子的自建手部锚点，但马上隐藏。这里隐藏的是同一个实体，素材和绑定关系仍在；到举花时只要把它显示出来。此处的自建锚点 ID 仅适用于案例中的 Profile，复制到其他模型并不能自动得到同样的手部位置。完成这组后，脚本停在人工检查点，再进入入场段落。

### 10.2 `forest-01`：灯先入、祥子随后入场

**第一组：对白之后移动灯。**

```webgal
灯:小祥，这边。 -notend;
setTransform:{"position":{"x":480,"y":0},"scale":{"x":1,"y":1}} -target=forest-tomori -duration=3000 -ease=easeOut -next;
```

灯先说话，随后她的立绘从开场的画外位置移动到画内横坐标 480。持续 3000 毫秒，缓动使移动末段减速。脚本此处留有手动检查提示；观看时先确认灯的位置与表情，不急着跳到后续镜头。

**第二组：网兜和祥子本体各写一次移动。**

```webgal
setTransform:{"position":{"x":-460,"y":-350},"scale":{"x":2.5,"y":2.5},"rotation":0} -target=forest-net -duration=3000 -ease=easeOut -next;
setTransform:{"position":{"x":-460,"y":0},"scale":{"x":1,"y":1},"rotation":0} -target=forest-sakiko -duration=3000 -ease=easeOut;
```

两条的横坐标同为 -460，但网兜层保持纵向 -350 和 2.5 倍尺寸，祥子本体保持纵向 0 和原尺寸。它们是两个立绘，所以必须分别移动。草帽绑在祥子头上，应随祥子本体移动；花仍绑定手部，但保持隐藏。`-next` 允许后续命令进入，不保证上一条 3000 毫秒动画已经结束，观察应以实际画面为准。

**第三组：站定后换动作和表情。**

```webgal
changeFigure:tomori/casual-2023/model.json -id=forest-tomori -duration=0 -motion=tomori/nf_left01 -expression=tomori/thinking02 -next;
changeFigure:sakiko/夏装捉虫小祥-捕虫网/model.json -id=forest-net -motion=sakiko/nod01 -expression=sakiko/default -duration=0 -next;
changeFigure:sakiko/夏装捉虫小祥/model.json -id=forest-sakiko -motion=sakiko/nod01 -expression=sakiko/default -duration=0;
```

这组三句改的是当前立绘的动作和表情，并没有重新创建附件。网兜层与祥子本体使用对应的点头动作，才能保持视觉上的配合。随后灯换笑容、祥子说“这里……连风都是凉的。”；这两步都在原脚本里，留给观看者确认人物站位与草帽跟随。

### 10.3 `forest-02`：帽子摇晃、消失与追逐

**第一组：人物先表现惊讶，帽子随后摇晃。**

```webgal
changeFigure:sakiko/夏装捉虫小祥-捕虫网/model.json -id=forest-net -motion=sakiko/surprised01 -expression=sakiko/default -duration=0 -next;
changeFigure:sakiko/夏装捉虫小祥/model.json -id=forest-sakiko -motion=sakiko/surprised01 -expression=sakiko/default -duration=0 -next;
```

两条立绘层都切换到惊讶动作。接下来原脚本有一条较长的临时动画语句，包含起点与六个连续关键帧，目标是草帽实体；每帧主要改变帽子的横纵位置与弧度制旋转，制造被风摇动的效果。该命令在案例原文件中是一整行，建议直接打开原脚本查看全部关键帧，不要只复制下面的说明文字。

```webgal
setTempAnimation:[{"position":{"x":0,"y":0},"rotation":0,"duration":0,"ease":"easeInOut"},{"position":{"x":-7,"y":-2},"rotation":-0.04,"duration":240,"ease":"easeInOut"},{"position":{"x":9,"y":-4},"rotation":0.055,"duration":240,"ease":"easeInOut"},{"position":{"x":-10,"y":-7},"rotation":-0.07,"duration":240,"ease":"easeInOut"},{"position":{"x":10,"y":-5},"rotation":0.065,"duration":240,"ease":"easeInOut"},{"position":{"x":-12,"y":-11},"rotation":-0.085,"duration":240,"ease":"easeInOut"},{"position":{"x":5,"y":-8},"rotation":0.04,"duration":240,"ease":"easeInOut"}] -target=forest-hat -continue;
```

这是原有的临时动画命令作用于插件附件目标，不是另一种附件创建命令。目标若误写成祥子立绘，摇晃的会是整个人，而不是帽子；`-continue` 在这段动画完成后推进。

**第二组：让仍戴在头上的帽子飞到画外并变透明。**

```webgal
setTransform:{"position":{"x":1850,"y":-750},"rotation":1.1,"alpha":0} -target=forest-hat -duration=1650 -ease=easeIn -continue;
stageEntity:detach -entity=forest-hat -coordinates=figure -continue;
stageEntity:hide -entity=forest-hat -duration=0 -continue;
```

关键顺序是先对**仍附着的帽子**施加 1650 毫秒的远移和淡隐，画外且透明之后才分离，最后再隐藏。分离本身只改变“是否跟着人物”，不会产生飞行动画；脚本用前面的变换完成观众看到的飞走效果。这里不宜把三句互换，否则可能在画面中看到突然脱离、跳位或残留。完成后祥子喊帽子、灯指出方向。

**第三组：人物追去，清除这一次的草帽实例。**

```webgal
setTransform:{"position":{"x":2250,"y":0},"scale":{"x":1,"y":1}} -target=forest-tomori -duration=1500 -ease=easeIn;
setTransform:{"position":{"x":2150,"y":-350},"scale":{"x":2.5,"y":2.5},"rotation":0} -target=forest-net -duration=1500 -ease=easeIn -next;
setTransform:{"position":{"x":2150,"y":0},"scale":{"x":1,"y":1},"rotation":0} -target=forest-sakiko -duration=1500 -ease=easeIn -next;
```

灯向右追出，网兜层和祥子本体也分别向右移出。帽子此前已隐藏，不应在追逐画面中突然出现。追逐之后还有一句结束旧帽生命周期：

```webgal
stageEntity:remove -entity=forest-hat -duration=0;
```

这句之后已不存在可直接重新绑定的旧帽实例；下一段必须重新创建草帽。花没有在这里删除，它仍是已隐藏、已绑定祥子手部的同一件。

### 10.4 `forest-03`：草帽自由返场，再戴回头上

**第一组：在画外重设人物，重新创建草帽。**

```webgal
setTransform:{"position":{"x":2050,"y":0},"scale":{"x":1,"y":1},"rotation":0} -target=forest-sakiko -duration=0 -ease=easeInOut -next;
attachment:add -figure=forest-sakiko -id=hat -entity=forest-hat -config=v2/夏日捉虫小祥的草帽-ffxmd2 -profile=user-profile-79d85c2b-c03c-4278-8efa-ccc3d60a0f09 -anchor=head -duration=1;
```

上一段旧帽已删，这里使用**同一附件配置**生成新的运行实例，并沿用舞台名 `forest-hat`。素材、保存参数和图片没有重新制作。重新创建的原因是清掉前一段风吹动画留下的局部变换。脚本同时把灯和网兜层也放在画外，准备统一返场；上面只列出与帽子重建直接相关的两句。

**第二组：在画外把新帽分离，给它自由位置。**

```webgal
stageEntity:detach -entity=forest-hat -coordinates=figure;
setTransform:{"position":{"x":2050,"y":200},"rotation":0,"alpha":1} -target=forest-hat -duration=0 -ease=easeInOut;
```

分离后，帽子不再自动跟祥子移动。下一句把它放在画外返场起点，并恢复不透明。由于操作发生在画外，观众主要看到的是随后独立移动进来的帽子，而不是头上突然摘帽的一帧。

**第三组：灯和自由帽各自返场。**

```webgal
setTransform:{"position":{"x":480,"y":0},"scale":{"x":1,"y":1}} -target=forest-tomori -duration=5100 -ease=easeInOut -next;
setTransform:{"position":{"x":-460,"y":200},"rotation":0,"alpha":1} -target=forest-hat -duration=5100 -ease=easeInOut -next;
```

灯回到右侧，已经分离的帽子则有自己的轨迹，目标停在祥子胸前附近。两条都写 5100 毫秒，却分别控制人物和自由实体；帽子不会因为灯或祥子的移动而自动改变目标。

**第四组：网兜层和祥子本体也分别返场。**

```webgal
setTransform:{"position":{"x":-460,"y":-350},"scale":{"x":2.5,"y":2.5},"rotation":0} -target=forest-net -duration=5100 -ease=easeInOut -next;
setTransform:{"position":{"x":-460,"y":0},"scale":{"x":1,"y":1},"rotation":0} -target=forest-sakiko -duration=5100 -ease=easeInOut;
```

这两条让祥子和网兜回到左侧，并保留两层之间的尺寸与高度差。此时帽子仍是自由实体，即使祥子之后换动作，帽子也不会自动跟着头走。连续命令中的 `-next` 不保证不同目标每一帧绝对同步；应按正常速度看返场终点。

**第五组：停留对白，再把自由帽戴回。**

```webgal
祥子:好险好险，差点被风吹跑了。;
stageEntity:reattach -entity=forest-hat -figure=forest-sakiko -profile=user-profile-79d85c2b-c03c-4278-8efa-ccc3d60a0f09 -anchor=head -duration=1500 -ease=easeInOut;
```

两句之间原脚本还有人物动作和表情变化，这里只列关键状态。重新绑定时仍使用这一次返场的 `forest-hat`，目标是祥子头部；它在 1500 毫秒的过程里移回保存的锚点位置。完成后帽子恢复跟随头部。若改写自己的脚本，不要在分离到重新绑定之间再创建第二顶同名帽子。

### 10.5 `forest-04`：第一次举花与近景

**第一组：人物换动作，显示开场已隐藏的花。**

```webgal
changeFigure:sakiko/夏装捉虫小祥-捕虫网/model.json -id=forest-net -motion=sakiko/smile01 -expression=sakiko/default -duration=0 -next;
changeFigure:sakiko/夏装捉虫小祥/model.json -id=forest-sakiko -motion=sakiko/smile01 -expression=sakiko/default -duration=0 -next;
stageEntity:show -entity=forest-flower -duration=0 -next;
```

祥子本体和网兜层一起切到举花段使用的动作；第三句把同一件花显示出来。花并未在此重新创建，仍附着在祥子的手部锚点。紧接着祥子说“这是我刚才摘的花。”，观众应能在这一镜头确认花和手的相对位置。

**第二组：背景和人物分别推进近景。**

```webgal
setTransform:{"position":{"x":92,"y":0},"scale":{"x":1.344,"y":1.344},"blur":1.2} -target=bg-main -duration=2000 -ease=easeInOut -next;
setTransform:{"position":{"x":668,"y":0},"scale":{"x":1.2,"y":1.2}} -target=forest-tomori -duration=2000 -ease=easeInOut -next;
```

这两句移动背景和灯，构成靠近祥子的画面；背景的目标与灯的目标不同。祥子和网兜还各有一条同样 2000 毫秒的变换：祥子变为 1.2 倍，网兜变为 3 倍并保持相对纵向偏移。花已附着手部，理论上应随祥子本体和手部动作一起变化，无需给花单独写镜头放大。原脚本随后安排灯的赞叹、祥子的表情和“我帮你戴上”，这些对白是下一段转移前的观看检查点。

### 10.6 `forest-05`：跟拍与靠近

**第一组：祥子及网兜切到靠近前的动作。**

```webgal
changeFigure:sakiko/夏装捉虫小祥-捕虫网/model.json -id=forest-net -duration=0 -motion=sakiko/smile06 -expression=sakiko/default -next;
changeFigure:sakiko/夏装捉虫小祥/model.json -id=forest-sakiko -duration=0 -motion=sakiko/smile06 -expression=sakiko/default -next;
```

两层立绘继续成对换动作。花仍在祥子手上，并保持可见；这里没有修改花的实体状态。若只改祥子本体而不改网兜层，两层姿态可能不再搭配。

**第二组：背景左移、灯进入双人构图。**

```webgal
setTransform:{"position":{"x":-100.86,"y":0},"scale":{"x":1.344,"y":1.344},"blur":1.2} -target=bg-main -duration=2500 -ease=easeInOut -next;
setTransform:{"position":{"x":260.86,"y":0},"scale":{"x":1.2,"y":1.2}} -target=forest-tomori -duration=2500 -ease=easeInOut;
```

背景与灯分别移动；祥子此时仍保持上一近景位置，组合成“镜头跟着双方关系调整”的效果。花没有离开祥子的手，捕虫网也还在自己的立绘层中。

**第三组：固定镜头，祥子带着花向灯靠近。**

```webgal
setTransform:{"position":{"x":-42.14,"y":-420},"scale":{"x":3,"y":3},"rotation":0} -target=forest-net -duration=1000 -ease=easeInOut -next;
setTransform:{"position":{"x":-42.14,"y":0},"scale":{"x":1.2,"y":1.2},"rotation":0} -target=forest-sakiko -duration=1000 -ease=easeInOut;
```

网兜和祥子同时向灯靠近，但各自维持原先的比例与纵向差。前面原脚本还把两层换成相应靠近动作。花应继续跟着祥子手部，而背景此组没有继续移动；这正好展示“人物移动”和“附件跟随”之间的区别。

### 10.7 `forest-06`：同一朵花转到灯的左耳

**第一组：先从祥子手部解绑。**

```webgal
stageEntity:detach -entity=forest-flower -coordinates=figure;
```

此时花从祥子手部锚点变成自由实体。`figure` 坐标模式用于保留分离瞬间的实际位置；命令本身并不会使花自动飞向灯。原脚本在这里留一个人工检查点，适合先看花是否从手部正确脱离。动作后立即快进到此处可能抓到中途姿态，不能用快进结果判断手部适配是否正确。

**第二组：把同一实体送到灯耳边。**

```webgal
stageEntity:reattach -entity=forest-flower -figure=forest-tomori -profile=tomori-casual-2023-semantic-v1 -anchor=ear-left -duration=1000 -ease=easeInOut;
```

目标人物改为灯，Profile 和锚点也换成灯这套外观的左耳；历时 1000 毫秒后，应重新成为随耳部移动的附着花。花的实体名和附件本体都没有改变，也没有再创建第二朵。这个转移能成立，是因为花的同一附件文件夹内已有祥子手部与灯左耳两套适配。若用户自己的附件只有手部适配，单独把目标名字改为另一人物并不能得到正确耳花。

### 10.8 `forest-07`：戴花后的反应、退场和清理

**第一组：祥子退开，灯带着耳花留下。**

```webgal
setTransform:{"position":{"x":-352.86,"y":-420},"scale":{"x":3,"y":3},"rotation":0} -target=forest-net -duration=1300 -ease=easeOut -next;
setTransform:{"position":{"x":-352.86,"y":0},"scale":{"x":1.2,"y":1.2},"rotation":0} -target=forest-sakiko -duration=1300 -ease=easeOut;
```

祥子本体与网兜分别后退并继续对齐；灯随后换动作和害羞表情。花已经绑定灯的左耳，因此这一段不应跟着祥子退开。对白“嗯，很适合灯”“……谢谢，小祥”让观众检查耳花是否仍在正确位置。

**第二组：灯先离场，祥子随后追上。**

```webgal
setTransform:{"position":{"x":2550.71,"y":0},"scale":{"x":1.2,"y":1.2}} -target=forest-tomori -duration=2000 -ease=easeIn;
setTransform:{"position":{"x":2443.57,"y":-420},"scale":{"x":3,"y":3},"rotation":0} -target=forest-net -duration=1500 -ease=easeIn -next;
setTransform:{"position":{"x":2443.57,"y":0},"scale":{"x":1.2,"y":1.2},"rotation":0} -target=forest-sakiko -duration=1500 -ease=easeIn;
```

第一句让灯向右离画；耳花应随灯一同走。灯说完“再往前看看吧”后，祥子和网兜分别向右追出。草帽此时已重新附着祥子头部，应随祥子离场；花则属于灯。这里可以同时检查两件附件在各自人物上的跟随关系。

**第三组：清理画面与实体。**

```webgal
changeBg:none -next;
stageEntity:remove -entity=forest-flower -duration=0 -next;
stageEntity:remove -entity=forest-hat -duration=0 -next;
```

先清背景，再显式删除花和帽的舞台实体，避免下一次播放继承它们。

**第四组：清除三层立绘。**

```webgal
changeFigure:none -id=forest-sakiko -duration=0 -next;
changeFigure:none -id=forest-net -duration=0 -next;
changeFigure:none -id=forest-tomori -duration=0 -next;
```

三层分别创建，也分别退出；删除祥子本体不会自动把网兜层一起删除。原脚本随后复位背景变换，再执行最后两句：

```webgal
say: -clear;
end;
```

再次观看时应从“开始游戏”进入，检查没有上一次留下的重复花帽、隐藏状态或层级残留。案例讲解的是**脚本意图和文件结构**；头部帽檐、手持花的位置、耳花遮挡、人物走位与正式导出效果仍需按正常速度实际观看。浏览器预览/独立网页已有卡顿和部分变换末尾跳位反馈，快进跨过动作也可能改变分离时捕获的姿态；详见第 11 节。演示素材中的人物模型、背景和附件图片用于对照教学；再次传播其中内容前，请核对相关素材的权利条件。

## 11. 已知问题与常见情况

以下内容针对本说明适用的 `.7` 安装包，其中另存修复已进入本包，其他未实现的能力仍按下列边界处理。遇到问题先保护自己的草稿和原文件，再按表中最短路径排查。

| 现象 | 先检查什么 | 建议动作 |
| --- | --- | --- |
| 安装拒绝或报占用 | Terre、制作器、预览和启动器是否仍在运行；错误中的目标路径 | 关闭自己打开的相关窗口后再试；保留原错误。不要手动删除锁或安装记录 |
| 制作器列表没有人物 | 角色目录是否已复制到安装后制作区的 `workspace/game/figure/`，或按钮导入是否成功；是否已有对应锚点组 | 按第 4 节核对最终模型路径并刷新立绘列表；无匹配 Profile 的模型从锚点制作器载入并按第 7 节制作锚点 |
| 人物可见、附件不显示 | 目标模型和 Profile/锚点是否匹配；是否真正保存并添加到当前游戏 | 用独立验证剧情检查错误码和首次出现，不靠制作区预览推断正式 Runtime |
| 换人物后附件位置不合适 | 新目标是否标为未校准 | 调整并保存该目标适配；不要覆盖原人物参数 |
| “保存附件”和“另存为新附件”结果不同 | 是否需要保留当前技术身份与旧剧情引用 | 修改原件用保存；制作独立副本才用另存 |
| 另存为新附件的旧身份冲突 | 当前实际安装修订是否为 `.7`，是否还开着旧版制作器 | 本包已在校验前生成新身份并重键保留适配；普通区只需显示名称。关闭旧版后重新启动，核对通知中的新路径和原件。若仍出现 `CREATOR_EXISTING_ADAPTATION_BINDING_MISMATCH`，保留草稿与完整诊断，不用旧版手改 ID 方法掩盖回归 |
| 新游戏中 Live2D 人物或附件黑屏 | Terre 中该游戏实际选用的引擎是否为配套 MyGO 3.2.1，游戏资源中 Live2D 库是否存在 | 先检查游戏的引擎选择与资源请求；选到官方 WebGAL 4.6.4 的案例曾出现 `live2d.min.js` 和 `live2dcubismcore.min.js` 404。不要把这类黑屏直接归因于附件命令 |
| 网页导出双击 `index.html` 黑屏 | 浏览器地址是否为 `file:///` | Windows双击同目录“启动游戏.cmd”，保持日志窗口；发布到网站使用HTTP(S)。不要把file直开黑屏直接归因为附件文件损坏 |
| 浏览器播放卡顿或末尾跳变 | 是 Terre 内嵌、新标签页、独立 HTTP 网页还是 EXE | 记下具体环境、场景与画面；这些表现已列已知问题，不能从某一环境推断全部一致 |
| 快进或 Terre“执行到此句”后附件位置不符合正常画面 | 是否跨过了 `stageEntity:reattach/remove`，或人物动作后立即 `detach` | 用户报告快进时 reattach/remove 仍可能等待过渡，detach 可能取到动作中途姿态；相关根因尚未完成真实 Runtime 复核。请按**正常速度**从动作前播放并检查关键状态，快进画面不要作为摆放参数验收依据 |
| Terre 反复切换 `a.txt→b.txt→a.txt` 后保存报会话冲突 | 编辑页内是否同时有未保存草稿或外部改稿 | 先复制并保护草稿，刷新整个 Terre 编辑页，重开文件核对磁盘内容后再保存；不要强行覆盖 |
| Terre 保存正式剧情失败，页底显示“场景未保存” | 剧情文件是否只读、被占用或出现保存错误 | **先复制或另行保护页面中的草稿，不要直接刷新或关闭**；按错误排查只读/占用后重试保存，确认出现保存成功再离开 |
| 已绑定游戏复制或改名后维护操作报身份/归属问题 | 安装记录中的目标游戏名与当前目录是否一致 | 暂停写入，保留游戏和资料库，联系维护者核对；不要删除 ownership 文件或反复覆盖。完整附件文件夹可复制，不代表已绑定游戏和宿主可随意改名搬家 |
| 收到别人导出的完整附件，能在列表里看到但修改保存报冲突 | 该目录是否手工复制进 `portable/`、是否从未进入本机受管记录 | 先备份，按第8.1节载入并明确确认登记；内容已手改时查看差异。不改manifest/ID绕过冲突；过期或损坏内容先核对 |

### 11.1 遇到失败，先判断“文件到底写进去没有”

| 看到的结果 | 该怎么判断 | 下一步 |
| --- | --- | --- |
